# FP-004 Owner UI addendum — read-only admin directory and local-calendar dates

**Status: PROPOSED / NOT YET APPROVED FOR IMPLEMENTATION.** The Owner requested the direction on 2026-11-19 and selected (a) read-only actual PasarGuard admin **ID and username only** and (b) **Gregorian date-only** controls, with local midnight based on a configurable IANA timezone (initially `Asia/Tehran`). This document is an implementation-grade proposal; approval of this exact addendum is still required before implementation or live-source activation. This does not renumber FP-004/005/006/007.

## 1. Goal and authoritative boundaries

- Improve the already implemented FP-004 Owner dashboard pricing editor without changing the approved pricing engine, `BIGINT` money/bytes, `CEIL`, rule precedence, effective-time exclusivity, or immutable history.
- Owner can select a billing admin by searchable `username (ID)` instead of typing a numeric ID; the **numeric ID remains canonical** for pricing, attribution and version history.
- Replace effective-start/effective-end UTC timestamp text inputs with **Gregorian `YYYY-MM-DD` date-only** controls interpreted as midnight in `FAIR_TIME_ZONE`, default `Asia/Tehran`. Local time and reporting boundaries use the same configured zone.
- The isolated public staging deployment remains Owner-authenticated, synthetic/shadow for financial and event data. The **only proposed exception** to the prior no-live-PasarGuard-data rule is bounded, read-only *admin IDs and usernames* fetched from an Owner-approved PasarGuard instance. No user, subscription, traffic, accounting, password, webhook or other private upstream data may enter staging.
- No connection directly to the PasarGuard database, no upstream writes, no financial postings or production deployment. This is an explicit architecture/security boundary change and requires approval of this document separately from the earlier UI direction.

## 2. PasarGuard read-only admin directory

Official PasarGuard source on its `main` branch: [`app/routers/admin.py`](https://github.com/PasarGuard/panel/blob/main/app/routers/admin.py) exposes `GET /api/admins/simple` with `admins:read_simple` permission. The `AdminsSimpleResponse` contains `{ admins: [{ id, username }], total }` ([`app/models/admin.py`](https://github.com/PasarGuard/panel/blob/main/app/models/admin.py)). The query supports `search`, `offset`, `limit`, `sort` and `all`; the chosen implementation must bound query size and avoid relying on unbounded `all=true`. The upstream [`app/routers/authentication.py`](https://github.com/PasarGuard/panel/blob/main/app/routers/authentication.py) supports `X-Api-Key`.

1. Integrate only in the **server-side Owner API**, never directly from the browser. Add a bounded authenticated `GET /api/v1/owner/directory/admins` for search/pagination. The response exposes only validated, bounded `{id: decimal-string, username: string}` pairs and pagination metadata.
2. The upstream URL is an Owner-configured fixed HTTPS base URL (`PASARGUARD_BASE_URL`); no request-supplied arbitrary URL, redirects, proxy credentials or dynamic host selection. Require certificate validation, short timeout, strict response size/row caps, and explicit upstream permission `admins:read_simple`. Access uses a dedicated limited API key mounted from an off-repository runtime secret, never a superuser password or an Owner browser token.
3. No passwords, tokens, raw upstream responses, profile fields, personal metadata or credentials in UI, logs, DB tables, CI artifacts or telemetry. Never store the API key in client bundles. No automatic retries on mutations (there are no upstream mutations). The directory is always read-only.
4. A short-lived in-memory cache may reduce upstream requests; it is *not authoritative financial state*. On upstream timeout, permission error, malformed data or missing credential, report a clearly labeled `DIRECTORY_UNAVAILABLE` state; never silently substitute a random admin. Provide an explicit manual-ID fallback to keep synthetic test pricing operable offline, with a warning that the upstream directory could not verify the ID.
5. Rename/deletion upstream changes display labels only. Existing immutable pricing versions and admin assignments keep their original numeric IDs, scoped by `sourceInstanceId`. Display unknown/stale ID as `شناسهٔ {id}`; never reassign to another admin by matching username. No import of real event/financial data or auto-reconciliation.
6. Owner chooses the upstream connection and provisions the read-only key separately. Without an approved/available key, all staging checks and deployment must still pass safely using the unavailable-directory fallback. Do not test against any actual PasarGuard host from CI.

## 3. Configurable timezone and Gregorian date-only pricing

1. Use a single explicit IANA config `FAIR_TIME_ZONE`, default `Asia/Tehran`, applied to Owner API, web UI and future reporting worker. Validate using IANA rules and fail clearly for an invalid zone; do not silently fall back to server timezone. Changing the setting requires a controlled service restart/redeploy, not a database rewrite.
2. Store all true instants as UTC `TIMESTAMPTZ` as before. Do **not** change the domain interface: pricing API continues receiving UTC ISO timestamps, and source `occurredAt` remains its verified original instant. Timezone affects how Owner date inputs become instants and how reports/grouped dates are displayed, not transaction ordering or historical money.
3. For date-only input `D` on an effective-start boundary, convert `D 00:00:00` in `FAIR_TIME_ZONE` to its exact UTC instant. The effective-end date denotes the **exclusive** start of that date at local midnight, retaining current `[from, until)` semantics. Empty end means unbounded. Explicit help text says, for example, `پایان 2027-01-01 یعنی تا پیش از شروع آن روز`.
4. Example: `2026-12-01` at midnight `Asia/Tehran` means `2026-11-30T20:30:00Z`; `2027-01-01` (exclusive) means `2026-12-31T20:30:00Z`. Validate end > start after conversion and reject invalid dates/ambiguous input before submitting. Do not assume every IANA zone has fixed UTC offset or a 24-hour day during DST transitions; use a tested timezone-aware library or equivalent correct IANA conversion.
5. Version creation and plan assignment each expose explicitly labeled date-only controls; do not silently take the assignment dates from the other form. Existing UTC rule rows are **not mutated**; read-only history displays local calendar/clock with the zone label. Historical effective ranges remain exact regardless of future configuration changes.
6. Price simulation preserves the ability to test an exact event instant: show an explicitly labeled local date+time field (rather than raw UTC text) and convert to UTC for the existing API. Do not alter quote math, precedence, volume, source or rounding.
7. The Owner UI obtains the configured timezone from an authenticated, allowlisted Owner API configuration response; no frontend hard-coded Tehran timezone. No secret ENV value is exposed. Dashboard event times and visible range boundaries use the same formatter/zone.

## 4. Reporting and midnight semantics

- Add a shared calendar-period utility yielding UTC `[start, end)` for a named local Gregorian day/week/month in the configured IANA timezone. A day starts at **00:00 local**, and the next day starts at its own **00:00 local** (do not add a fixed 86,400 seconds).
- Daily reports/aggregations and future scheduled local-midnight report triggers must use that utility. Do not alter the source timestamp or the UTC persisted transaction records; reports still aggregate only immutable accounting transactions. Report jobs must retain idempotent delivery, persisted state and human approval when later separately implemented.
- **No daily-midnight scheduled report currently exists in the deployed FP-003B UI**; its `1h/24h/7d/30d` summary filters are rolling time windows. This addendum must not pretend such a scheduler already exists. Keep existing rolling filters explicitly labeled, and if adding local-calendar `امروز`/`دیروز` views, implement them as distinct selections with non-overlapping tests; future scheduler/notification work remains outside this addendum.
- Changing `FAIR_TIME_ZONE` changes **future local calendar boundaries and display** only; it must not silently recompute/rewrite earlier stored report snapshots, financial amounts or pricing versions. A future report scheduler should persist its chosen zone and cutoff per report instance for reproducibility.

## 5. Tests and release gates

- Pure unit and UI contract tests for Gregorian valid/invalid/leap dates; timezone conversion at local midnight, month/year rollover and local exclusive end boundaries; dates parsed/displayed in `Asia/Tehran` and at least one DST-observing IANA zone; changing `FAIR_TIME_ZONE` without changing persisted UTC timestamps.
- Pricing regression tests proving admin override > assigned plan > default, exact fixed/Mixed/per-GiB behavior, immutable versions, no overlap and identical price on the same UTC source instant regardless of display timezone.
- Upstream HTTP contract tests with synthetic mock server only: paginated `{admins,total}` success, empty list, invalid/duplicate IDs, enormous total, timeout, expired/insufficient key (401/403), redirect rejection, malformed/overlong data, and server error. Assert only `{id,username}` crosses the Owner API boundary; no real upstream call in CI.
- Access tests for unauthenticated directory requests, host/URL injection, cache isolation, source-scoped ID selection, absence of credentials in logs/browser bundles and explicit manual-ID fallback.
- Desktop/mobile Owner UI tests verifying searchable `username (ID)`, disabled/unavailable state, date-only fields, accurate local previews and readable timezone labels. Maintain unchanged public TLS/Owner authentication/synthetic financial safety, GitHub CI gates and automatic rollback.
- Implement on a dedicated branch and a **Draft PR** after human Owner explicitly approves this specification. Only human Owner marks Ready and merges after Review/QA/CI, followed by Staging smoke verification. Do not configure a real upstream API key or activate access without separate Owner-controlled secret provisioning and a verified limited permission.
