Preserve `BIGINT` money/bytes, `CEIL` and immutable historical charges, while **explicitly revising** the previous default-plan/version UI and effective-rule precedence under the Owner's approved local-group/package design. This is a future implementation change, not a claim that the deployed quote engine has already changed.

The *selected end date is inclusive*; internal storage is still UTC half-open `[from, until)`, where the exclusive instant is midnight of the **following Jalali day**. Local time and reporting boundaries use the same configured zone.
- The isolated public staging deployment remains Owner-authenticated, synthetic/shadow for financial and event data. The **only proposed exception** to the prior no-live-PasarGuard-data rule is bounded, read-only *admin IDs and usernames* fetched from an Owner-approved PasarGuard instance. No user, subscription, traffic, accounting, password, webhook or other private upstream data may enter staging.
- No connection directly to the PasarGuard database, no upstream writes, no financial postings or production deployment. This is an explicit architecture/security boundary change and requires approval of this document separately from the earlier UI direction.

## 2. PasarGuard read-only admin directory

Official PasarGuard source on its `main` branch: [`app/routers/admin.py`](https://github.com/PasarGuard/panel/blob/main/app/routers/admin.py) exposes `GET /api/admins/simple` with `admins:read_simple` permission. The `AdminsSimpleResponse` contains `{ admins: [{ id, username }], total }` ([`app/models/admin.py`](https://github.com/PasarGuard/panel/blob/main/app/models/admin.py)). The query supports `search`, `offset`, `limit`, `sort` and `all`; the chosen implementation must bound query size and avoid relying on unbounded `all=true`. The upstream [`app/routers/authentication.py`](https://github.com/PasarGuard/panel/blob/main/app/routers/authentication.py) supports `X-Api-Key`.

1. Integrate only in the **server-side Owner API**, never directly from the browser. Add a bounded authenticated `GET /api/v1/owner/directory/admins` for search/pagination. The response exposes only validated, bounded `{id: decimal-string, username: string}` pairs and pagination metadata.
2. The upstream URL is an Owner-configured fixed HTTPS base URL (`PASARGUARD_BASE_URL`); no request-supplied arbitrary URL, redirects, proxy credentials or dynamic host selection. Require certificate validation, short timeout, strict response size/row caps, and explicit upstream permission `admins:read_simple`. Access uses a dedicated limited API key mounted from an off-repository runtime secret, never a superuser password or an Owner browser token.
3. No passwords, tokens, raw upstream responses, profile fields, personal metadata or credentials in UI, logs, DB tables, CI artifacts or telemetry. Never store the API key in client bundles. No automatic retries on mutations (there are no upstream mutations). The directory is always read-only.
4. A short-lived in-memory cache may reduce upstream requests; it is *not authoritative financial state*. On upstream timeout, permission error, malformed data or missing credential, report a clearly labeled `DIRECTORY_UNAVAILABLE` state; never silently substitute a random admin. Provide an explicit manual-ID fallback to keep synthetic test pricing operable offline, with a warning that the upstream directory could not verify the ID.
5. Rename/deletion upstream changes display labels only. Existing immutable pricing versions and admin assignments keep their original numeric IDs, scoped by `sourceInstanceId`. Display unknown/stale ID as `شناسهٔ {id}`; never reassign to another admin by matching username. No import of real event/financial data or auto-reconciliation.
6. Owner chooses the upstream connection and provisions the read-only key separately. Without an approved/available key, all staging checks and deployment must still pass safely using the unavailable-directory fallback. Do not test against any actual PasarGuard host from CI.

## 3. Configurable timezone and Jalali date-only pricing

1. Use a single explicit IANA config `FAIR_TIME_ZONE`, default `Asia/Tehran`, applied to Owner API, web UI and future reporting worker. Validate using IANA rules and fail clearly for an invalid zone; do not silently fall back to server timezone. Changing the setting requires a controlled service restart/redeploy, not a database rewrite.
2. Store all true instants as UTC `TIMESTAMPTZ` as before. Existing pricing API UTC instants and original source `occurredAt` remain unmodified during the transition; the new nightly price resolver additionally uses duration days and the **frozen end-of-day group** rather than blindly repricing at the source instant. Timezone changes never rewrite historical money.
3. For Jalali date-only start `D`, convert local `D 00:00:00` in `FAIR_TIME_ZONE` to an exact UTC instant. For selected **inclusive** end `E`, compute local midnight of the **calendar day following E**, convert that to the exclusive UTC bound, and retain `[from, until)` internally. Empty end means unbounded; empty start defaults to today's local Jalali date. Explicit help text says `تاریخ پایان نیز شامل اعتبار است`.
4. Example: a package assignment from **۱۴۰۵/۰۹/۱۰ through ۱۴۰۵/۰۹/۳۰**, inclusive, is effective from local midnight of ۱۰ آذر until **just before midnight beginning ۱ دی**. Validate calendar dates and start/end ordering, including ۳۱ شهریور and leap-year ۳۰ اسفند. Never add 86,400 seconds for a local day in a DST-observing zone; use the approved tested Jalali library and IANA time zone conversion.
5. Package **definition** exposes no validity dates; package assignment to a group/admin exposes date-only controls. Existing UTC rule rows are **not mutated**; read-only history displays Jalali calendar dates and local clocks with the zone label. Historical effective ranges remain exact regardless of future configuration changes.
6. Price simulation preserves the ability to test an exact event instant: show an explicitly labeled local date+time field (rather than raw UTC text) and convert to UTC for the existing API. Do not alter quote math, precedence, volume, source or rounding.
7. The Owner UI obtains the configured timezone from an authenticated, allowlisted Owner API configuration response; no frontend hard-coded Tehran timezone. No secret ENV value is exposed. Dashboard event times and visible range boundaries use the same formatter/zone.

## 4. Reporting and midnight semantics

- Add a shared calendar-period utility yielding UTC `[start, end)` for a named local **Jalali** day/week/month in the configured IANA timezone. A day starts at **00:00 local**, and the next day starts at its own **00:00 local** (do not add a fixed 86,400 seconds).
- Daily settlements/reports and future scheduled jobs must use that utility. Do not alter source timestamps or persisted UTC events. **No financial calculations occur during the day**: the configurable nightly worker posts immutable per-admin/day charges. Weekly/monthly reports aggregate the stored final daily charges only. One ambiguous day is held independently while later days can still be delivered; weekly/monthly wait for the incomplete daily periods.
- **No daily-midnight scheduled report currently exists in the deployed FP-003B UI**; its `1h/24h/7d/30d` summary filters are rolling time windows. This addendum must not pretend such a scheduler already exists. Keep existing rolling filters explicitly labeled, and if adding local-calendar `امروز`/`دیروز` views, implement them as distinct selections with non-overlapping tests; future scheduler/notification work remains outside this addendum.
- Changing `FAIR_TIME_ZONE` changes **future local calendar boundaries and display** only; it must not silently recompute/rewrite earlier stored report snapshots, financial amounts or pricing versions. A future report scheduler should persist its chosen zone and cutoff per report instance for reproducibility.
